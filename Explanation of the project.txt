3. The AI is not just a chatbot

This is very important.

Your teacher explicitly says:

AI must be a meaningful part of the product.

So don’t build:

Ticket → ChatGPT → response

and call it AI integration.

Instead, your AI should perform several tasks.

When a ticket arrives:

1. Understand it

Example:

“I paid for premium but my account still says free.”

AI understands:

Intent:
Payment/subscription problem

2. Categorize it

For example:

Category:
Billing

Possible categories:

ACCOUNT
BILLING
TECHNICAL
REFUND
FEATURE_REQUEST
SECURITY
OTHER

3. Determine urgency

For example:

Priority: HIGH
Reason:
Customer has paid but cannot access purchased service.

4. Generate a suggested response

For example:

Hi John,
Thanks for contacting us. I understand that you've
completed your payment but your account still shows
the free plan...
Regards,
Support Team

But here’s the important part.

⸻

4. AI must NOT blindly answer everything

This is one of the most important requirements.

Suppose the customer says:

“I want a refund.”

Your AI shouldn’t invent:

“Sure, our refund policy allows refunds within 30 days.”

What if your company doesn’t have a 30-day refund policy?

The assignment explicitly says AI must not invent company policies, prices, refund rules, etc.

So you need some kind of company knowledge source.

For example:

Company Knowledge
│
├── Refund policy
├── Pricing
├── Subscription policy
├── Account policy
├── Technical troubleshooting
└── Support guidelines

The AI can only use information supplied by your system.

This is where you can make the project significantly better.

⸻

5. You need a Human-in-the-Loop system

Not every ticket should be automatically handled.

You should design rules such as:

Automatically handled

"What are your opening hours?"
→ AI answers
→ Send automatically

Human approval required

"I want a refund."
→ AI analyzes
→ AI drafts response
→ Human reviews
→ Human approves
→ Email sent

Definitely human

"I think someone hacked my account."
→ HIGH/CRITICAL
→ AI does NOT automatically respond
→ Human support required

This gives you a very good architecture:

                AI
                 │
       ┌─────────┴─────────┐
       │                   │
   Low Risk            High Risk
       │                   │
       ▼                   ▼
Automatic             Human Review
Response                  │
                          ▼
                    Approve / Edit
                          │
                          ▼
                         Send

⸻

6. You MUST build an AI Agent

This is different from simply calling an LLM API.

Your project needs at least one AI agent.

For example, create a:

SupportAgent

It could have tools such as:

get_ticket()
search_company_knowledge()
get_customer_history()
update_ticket_status()
draft_response()
send_email()

The agent receives:

Ticket #1042
Customer information
Conversation history
Company policies

and decides what it needs to do.

For example:

SupportAgent
1. Read ticket
2. Understand issue
3. Search company knowledge
4. Determine category
5. Determine priority
6. Draft response
7. Decide whether human approval is required
8. If approved → send response

That is a meaningful agent.

⸻

7. Agent Skill

This is another requirement that could easily be misunderstood.

You need to create at least one reusable Agent Skill.

Think of a Skill as a reusable set of specialized instructions/knowledge.

For example:

CustomerSupportSkill

Purpose:
Handle incoming customer support requests.
Rules:
1. Never invent company policies.
2. Always search company knowledge before
   answering policy-related questions.
3. Refund requests require human approval.
4. Security-related issues require human review.
5. Never send an email without approval for
   sensitive actions.
6. If confidence is low, escalate to human support.

Then your agent can use this Skill.

The assignment specifically wants you to understand why this is separate from one giant prompt.

⸻

8. MCP is another major requirement

This is probably the most unfamiliar part if you haven’t worked with MCP before.

You need to expose at least 3 useful capabilities through an MCP server.

For example:

                 MCP SERVER
                     │
       ┌─────────────┼─────────────┐
       │             │             │
       ▼             ▼             ▼
 get_ticket()   search_tickets()  update_ticket()

An external AI client connected to your MCP server could then say:

“Show me all urgent unresolved tickets.”

and use:

search_tickets(
    status="open",
    priority="urgent"
)

Or:

“Show me ticket #1042.”

→

get_ticket(1042)

You could expose:

Tool 1

get_support_ticket

Read-only.

Tool 2

search_support_tickets

Read-only.

Tool 3

update_ticket_status

Write operation.

Potentially:

Tool 4

get_customer_history

Read-only.

Tool 5

draft_support_response

AI operation.

Tool 6

send_support_response

Dangerous/write operation → should require appropriate authorization/approval.

This distinction between read-only and action tools is something you’ll likely be questioned about.

13. AI_DECISIONS.md

This is actually a clever requirement.

They don’t want:

“We used ChatGPT.”

They want evidence that you critically evaluated AI-generated code/designs.

For example:

AI Decision #1
AI suggested storing the entire customer conversation
inside the support_tickets table.
We rejected this because conversations are naturally
one-to-many and should be stored separately in
ticket_messages.

Another:

AI Decision #2
AI suggested allowing the agent to automatically
send refund responses.
We rejected this because refund-related actions
require human approval.

Another:

AI Decision #3
AI suggested exposing a send_email MCP tool without
authorization.
We rejected this because it could allow an external
AI client to send unauthorized messages.

These would be excellent examples.

        ↓
Validation error

        ↓
Validate output
        ↓
Retry / mark AI failed
        ↓
Human review
Resend fails
        ↓
Don't mark email as successfully sent
        ↓
Record failure
        ↓
Allow retry
AI confidence < threshold
        ↓
Human review
Unauthorized user
        ↓
Reject request

This is why this is more than just a CRUD application.

16. Suggested tech stack

Since you’re already working with web development, I would keep the stack relatively simple.

Frontend

React / Next.js

Backend

FastAPI or Next.js API routes.

Since you’ve worked with FastAPI before, FastAPI would be a reasonable choice.

Database

Supabase PostgreSQL

Authentication

Supabase Auth

Email

Resend

AI

An LLM API of your choice.

Agent

Use an agent framework/SDK that your team can actually explain, rather than adding a complicated framework just for the sake of it.

MCP

A dedicated MCP server exposing your support-system operations.

Deployment

For example:

Frontend → Vercel
Backend → Render/Railway/etc.
Database → Supabase
Email → Resend
MCP → deployed backend/service

The exact providers aren’t mandated, so choose based on what your team can confidently maintain.

18. What you should NOT do

There are several traps in this assignment.

❌ Don’t build a beautiful UI first

The document explicitly says visual appearance isn’t the priority.

❌ Don’t make AI a simple chatbot

The AI needs to actually participate in the support workflow.

❌ Don’t let AI invent policies

This is explicitly prohibited.

❌ Don’t give the agent unrestricted database access

Give it specific tools with controlled permissions.

❌ Don’t expose dangerous MCP tools without thinking about authorization

Especially things like:

send_email()
delete_ticket()
refund_customer()

❌ Don’t blindly copy AI-generated code

You’ll be questioned individually.

❌ Don’t let everyone commit using one account

They explicitly want meaningful contributions from all three members.
